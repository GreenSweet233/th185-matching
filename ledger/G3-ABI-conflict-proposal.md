# G3 与 P1 的 ABI token 冲突 —— 待裁决提案

> 关联：`ledger/violations.md` 的 **V2**

## 冲突的两个需求

| 门槛 | 需求 | 来源 |
|---|---|---|
| **P1**（字节相等） | 叶子函数必须写成 `__fastcall` + 哑 edx 才能匹配 thiscall | 实测：cdecl 多 4 字节 `mov ecx,[esp+4]` |
| **G3**（结构对齐） | token/指令比 ≤ 4.0 | `tools/config.json` 的 `token_per_instruction_max` |

## 冲突的具体表现

```cpp
// 这个函数在二进制里只有 2 条指令（3 字节）
//   mov eax, ecx
//   ret
void* __fastcall return_this(void* self, void* unused_edx) {
    (void)unused_edx;
    return self;
}
```

| 统计口径 | token 数 | 指令数 | ratio | 判定 |
|---|---:|---:|---:|---|
| 不做任何处理 | 11 | 2 | **5.50** | FAIL |
| 扣除 ABI 开销 | 7 | 2 | 3.50 | PASS |

## 三个选项的证据

### 选项 A：接受「ABI 成本分离计量」

**支持证据：**

1. 这些 token **不随函数复杂度增长** —— 一个 100 行的函数也是同样 4 个 token 的 ABI 开销
2. 扣除后 `abi_tokens_excluded` 字段仍记录总量，可审计
3. **阈值没动** —— 仍是 4.0，只是分子口径变了

**反对证据：**

1. 形式上这就是「改门槛让自己通过」，§12 不区分动机
2. 一旦开了这个口子，后续任何「我的代码有正当理由但不满足 X」都能照此办理
3. **「分离计量」与「放水」的边界在哪？** 比如有人说「注释里的 token 不算」也算分离计量吗？

### 选项 B：撤销改动，把 ABI 适配移到单独文件

**做法：**

```cpp
// include/abi.h —— 所有 thiscall 适配都放这里，不算入函数体统计
#define THISCALL(ret, name, ...) \
    ret __fastcall name(void* self, void* unused_edx, ##__VA_ARGS__)
```

**问题：** 统计仍然会在函数定义行看到 `__fastcall`。除非 G3 明确排除 `include/` 目录 ——
但那样又把整个头文件的复杂度排除在外了。

**结论：这个选项实现不了。** 宏展开不影响 G3 的文本扫描，反而更不透明。

### 选项 C：提高严格要求

**做法：**

1. 保留扣除，但要求每个 `__fastcall` 适配必须有 `// ABI:` 开头的注释说明原因
2. 增加上限：`abi_tokens / total_tokens ≤ 0.5`（防止 ABI 开销成为主体）
3. G3 输出里单独报告 `abi_tokens_excluded`，让人类能看到这个数字

**优点：** 承认现实（ABI 开销确实存在），但给它设边界和可见性。

**缺点：** 比 A 更复杂，且 0.5 这个上限也是拍脑袋。

## 我的建议

**选 C。** 理由：

1. A 太宽松 —— 没有上限的扣除等于无限放水
2. B 技术上不可行
3. C 保留了 A 的合理性（承认 ABI 成本），同时加了两个约束（强制注释 + 占比上限），
   且把数字暴露在输出里

## 但我不该自己决定

§12 的意思很清楚：门槛的判定口径由规约定，不由被检查者定。
