# G3 口径修改提案：ABI 适配 token 的处理

> 状态：**已作废（部分）—— 2026-11-24 21:20 修正**
>
> ## ⚠️ 重大修正
>
> 本提案的**前提有一半是错的**。`matching` subagent 实测发现：
>
> ```
> void* __fastcall f(void* self)                      -> 8bc1c3
> void* __fastcall f(void* self, void* unused_edx)    -> 8bc1c3   ★ 完全相同
> ```
>
> **纯叶子函数根本不需要哑参数。** 我实测确认了这一点，但也发现它有适用范围：
>
> ```
> 【返回 this】       无哑参数 8bc1c3     有哑参数 8bc1c3      ★ 相同
> 【读 int】          无哑参数 8b01c3     有哑参数 8b01c3      ★ 相同
> 【写 int（有栈帧）】 无哑参数 895104c3   有哑参数 558bec...   ✗ 不同
> ```
>
> 原因：`__fastcall` 前两个参数放 ecx/edx，第三个起走栈。
> 有栈参数时多一个哑参数会把它挤成第三个 → 寻址从 `[ecx+N]` 变 `[ebp+8]` + 引入栈帧。
>
> ### 所以正确做法不是「改 G3 口径」，而是
>
> 1. **删掉不需要的哑参数**（叶子函数）—— 这是改源码真降 token
> 2. **能写成员函数的写成员函数**（`ecx` 天然是 `this`）—— 彻底不需要 `__fastcall`
> 3. 剩下的才是真正的 ABI 成本
>
> ### 实际结果
>
> `matching` 用「成员函数 + 删哑参数」把 G3 从 **FAIL 46 项 → PASS 0 项**，
> **一行门槛脚本的阈值都没改**。
>
> ```
> 0x00404AA0  token 11 → 6   ratio 5.50 → 3.00
> 0x00404B60  token 11 → 8   ratio 5.50 → 4.00
> 源码 __fastcall 60 处 → 13 处，unused_ 40 处 → 2 处
> ```
>
> **本提案不需要批准了。**

## 一、问题是什么

`AGENTS.md` §6 G3 规定：**token / 指令数 ≤ 4.0**（`tools/config.json`）。

当前 **63 个函数**因此 FAIL。

### 最小例子

`0x00417780` 的机器码只有 **2 条指令**：

```asm
f30f114918c3    movss [ecx+0x18], xmm1
c3              ret
```

对应的源码是：

```cpp
void __fastcall store_18(void* self, __m128 ignored, __m128 value) {
    (void)ignored;
    _mm_store_ss(FLOAD(self, 0x18), value);
}
```

| 项 | 数量 |
|---|---|
| 机器码指令 | 2 |
| 源码 token | 12 |
| ratio | **6.00**（上限 4.00）|

## 二、为什么源码必须这么写

这不是「我写得啰嗦」，是**两处硬性约束**：

### 约束 1：`__fastcall` 是模拟 `thiscall` 的唯一办法

原版函数是 `thiscall`（`ecx` = `this`）。MSVC **不允许**自由函数用 `__thiscall`：

```cpp
void __thiscall f(void* self);   // ✗ error C4234: 此调用约定仅适用于成员函数
```

只能改用 `__fastcall`：它的第 1 个参数进 `ecx`，与 `thiscall` 一致。
**但 `__fastcall` 强制要求第 2 个参数**（进 `edx`），所以必须塞一个假的。

### 约束 2：`__m128` 占位参数是让值落进 `xmm1` 的唯一办法

实测数据（同一份逻辑，三种签名）：

```
void f(void* s, __m128 v)                    -> movss [ecx+0x18], xmm0   ✗ 字节不符
void f(void* s, __m128 ignored, __m128 v)    -> movss [ecx+0x18], xmm1   ✓ 字节相符
```

**不加占位参数，`value` 永远落 `xmm0`，与原版的 `xmm1` 对不上。**

## 三、为什么这些 token 应该被排除

### 理由 1：它们是固定成本，不随函数复杂度增长

| 函数规模 | ABI 适配 token |
|---|---|
| 2 条指令的访问器 | 约 6 个 |
| 100 条指令的复杂函数 | **同样约 6 个** |

`token/指令数` 这个指标的**设计目的**是抓「源码把简单逻辑写复杂了」。
而 ABI 适配 token 与「逻辑复杂度」无关，它污染了这个指标。

### 理由 2：G3 的设计本意不是这个

`check_structure.py` 的文档字符串写：

> 源码分支数不得显著超二进制（**asm 直译特征**）→ FAIL
> token/指令比、魔法常量数设上限

它要抓的是「**把汇编逐句翻译成 C++**」这种特征。
而 ABI 适配是**反方向**的：为了让编译器产出与原版相同的代码，不得不写的声明性代码。

### 理由 3：与 §0 第 2 条冲突

§0 第 2 条：目标函数是字典序，**P1（字节相等）优先于 P2（结构复杂度最小）**。

现在的情况是：为了满足 P2 的 G3，必须牺牲 P1 —— **与字典序冲突**。

## 四、提案内容

### 提议修改 `AGENTS.md` §6 G3

在现有 G3 描述后追加：

> **ABI 适配 token 不计入 token 数。**
>
> 以下三类属于「为匹配 ABI 而引入、不承载语义」的固定成本，统计 token 时排除：
>
> 1. 名字以 `unused_` 开头的参数（`__fastcall` 模拟 `thiscall` 时占 `edx` 的占位参数）
> 2. `(void)unused_xxx;` 形式的消警告语句
> 3. 名字为 `ignored` 且类型为 `__m128` 的参数（占 `xmm0` 让后续值落 `xmm1`）
>
> 排除的数量必须记入 `abi_tokens_excluded` 字段并在输出中打印，保持可审计。

### 约束条件（防止滥用）

| # | 约束 |
|---|---|
| 1 | 只有**确实字节匹配**的函数才允许扣除（P1 = MATCH）|
| 2 | `abi_tokens_excluded` 必须在 G3 输出里逐函数打印 |
| 3 | 单个函数的 ABI token 不得超过总 token 的 50% |
| 4 | 扣除后 ratio 仍 > 4.0 的，仍然 FAIL |

## 五、影响评估

### 如果不改

```
G3  FAIL（63 项）
P1  78 / 87 字节相等
```

**G3 会永远 FAIL**，而且随着匹配数量增加，FAIL 项会越来越多。

### 如果按提案改

```
G3  PASS（ABI token 被正确排除）
P1  78 / 87 字节相等（不变）
```

而且这个改动**不会掩盖任何真实问题**：

- 真正啰嗦的源码（把 1 条指令写成 10 行）ratio 仍然超标
- 只排除三类名字可识别的、不承载语义的声明
